## Summary

Il progetto non ha disegnatori e deve essere verificabile a ogni passo nella sessione di sviluppo. Si costruisce come pagina web statica (HTML, Canvas 2D per il mondo, DOM per HUD e cartiglio, JavaScript a moduli ES) senza framework né passo di build; l'eseguibile Windows si ottiene impacchettando la cartella (Tauri o Electron) a fine progetto.

## Context

Il tentativo v1 in Godot è fallito sulla produzione dell'arte, non sul motore; ma Godot non si può
eseguire né osservare nella sessione cloud in cui il gioco viene sviluppato, quindi ogni verifica
visiva passava per l'autore. Il browser invece si guida con Playwright, produce screenshot ed è
giocabile da un link. Il genere (stanze 13×7, poche decine di sagome, luci procedurali) sta
comodamente dentro Canvas 2D.

## Decision

- Canvas 2D per il mondo di gioco (stanze, attori, luci, effetti); DOM per HUD, cartiglio, menu
  (testo che va a capo, accessibilità, font).
- JavaScript a moduli ES nativi, senza bundler. Nessuna dipendenza esterna salvo Google Fonts
  (Cinzel, Cormorant Garamond) con fallback serif.
- Risoluzione logica 1280×720, scalata al contenitore mantenendo il rapporto; pixel ratio del
  dispositivo rispettato per nitidezza.
- Server statico locale per lo sviluppo (`python3 -m http.server`), GitHub Pages o artifact per la
  distribuzione web, impacchettamento desktop a fine progetto.

## Alternatives Considered

- **Godot 4.6** (v1): migliore per un gioco d'azione in generale, ma non osservabile nella sessione di
  sviluppo e il framework di progetto resta utilizzabile anche senza.
- **WebGL/PixiJS**: più veloce per migliaia di sprite; non serve con ≤ 40 sagome; aggiunge una
  dipendenza e un build.
- **Phaser**: framework completo, ma impone il suo ciclo e il suo loader; il nostro renderer è
  l'identità del gioco e va scritto a mano.

## Consequences

- Positive: verifica continua con screenshot; nessun toolchain; deploy immediato.
- Negative: niente editor di scene; input gamepad meno uniforme tra browser; packaging desktop da
  fare a mano; prestazioni da sorvegliare se le luci crescono (budget in `architecture.md` §6).
- Il framework CCGS non conosce "Web": le skill che cercano `docs/engine-reference/web` dichiarano
  NOT SOURCEABLE e non bloccano.
